# 醫療服務入口 MVP／Prototype 設計規格

## 0. 結論

階段 1 採用「**平台化行政服務入口互動原型**」。它以可點擊的 Web Prototype 模擬使用者輸入、AI 行政欄位整理、已標示來源的服務選項、使用者確認、預約交接模擬與狀態回傳。所有資料使用合成資料或公開目錄的固定快照；所有外部動作使用模擬 Adapter。

本原型要證明三項能力：

1. 使用者能以低門檻文字、語音轉文字或欄位開始搜尋服務。
2. LLM 能在受控 schema 內整理行政條件，且使用者可看見與修改每一項欄位。
3. 工具與合作端接口能以可回溯、不可偽造預約的方式完成「選擇後交接」流程。

平台整合經驗證的服務資訊與合作端工具，將一般人難以理解的服務條件、可取得資源與正式入口轉為低門檻流程。醫療機構、檢驗所、居家服務團隊與持照人員提供實際服務。平台不提供診療、採檢、檢體處理、結果說明或醫療決定。

本原型不驗證市場需求、付費意願、合作端意願、實際時效、醫療可行性或法規核准。這些事項需以訪談、合作端邀約、法務審查及正式資料串接另行驗證。

## 1. 命題與思考原因

### 1.1 要解決的問題場景

使用者在非緊急狀況下，常需跨越多個入口才能找到可聯絡或可預約的服務：搜尋院所、確認地址與時段、理解是否有對應服務、撥電話或跳轉預約頁。原始研究已界定平台只處理服務發現、行政條件整理、地圖／電話、預約交接與履約狀態，不處理病情判讀、檢傷、診斷、治療或檢驗結果解讀。

### 1.2 為何選擇此方案

此方案以最小技術與資料範圍展示完整使用者路徑。它把 LLM 放在降低輸入與理解門檻的位置，將事實性服務資料、可預約性與狀態交給資料來源或 Adapter。平台像 MCP 用戶端一樣協調並調用受權工具，資源由外部專業服務端持有與履行。此分工可避免模型虛構服務可用性，也能在尚未取得合作端 API 前預先驗證介面、工具權限、狀態機與稽核需求。

### 1.3 方案選擇與篩選

| 路徑 | 做法 | 優點 | 缺口 | 決定 |
|---|---|---|---|---|
| A. 行政服務入口互動原型 | LLM 整理行政條件，固定資料集找服務，模擬預約與狀態。 | 可展示端到端互動；不接觸真實醫療資料；可測工具邊界。 | 無法證明真實可預約性與市場需求。 | 選定。 |
| B. 目錄與深連結導覽原型 | 僅提供官方目錄、地圖、電話與外部連結。 | 開發量最低，風險最低。 | 無法驗證交接狀態、確認點與合作端 Adapter。 | 作為 A 的降級模式。 |
| C. 合作端沙盒編排原型 | 模擬合作端 API、付款與狀態 webhook，採 FHIR Appointment 交換模型。 | 最接近後續交易閉環。 | 資料模型、權限與狀態管理成本高；單獨執行會過早。 | 列為 A 通過後的下一階段。 |

### 1.4 參照案例與目標功能

| 參照 | 可參照的功能結構 | 本原型採用的部分 | 限制 |
|---|---|---|---|
| 美團健康相關服務入口 | 多服務入口、服務履約網與線下交接。 | 從單一對話入口走到可選服務與交接狀態的結構。 | 不採用其市場、醫療資格、時效或商業數字。 |
| Halodoc | 平台入口與醫療服務端承接的分工。 | 平台顯示服務選項，正式醫療流程由服務端負責的責任切分。 | 僅作流程結構參照，不外推臺灣合規性。 |
| 健保署院所查詢資料 | 院所名稱、地址、電話、服務項目與固定時段。 | Prototype 的公開資料欄位與來源標籤樣式。 | 不以公開資料推論即時可受理量或到府能力。 |

## 2. 產品範圍與安全界線

### 2.1 平台責任模型

| 角色 | 責任 | 平台可調用的能力 | 平台不得取代的能力 |
|---|---|---|---|
| 平台 | 聚合已驗證資料、簡化服務條件、協調 MCP／API、取得確認、保存交接與稽核紀錄。 | 服務目錄、地圖、正式預約入口、合作端可揭露的狀態。 | 診療、採檢、醫療分級判斷、檢體處理、結果解讀與醫療決策。 |
| 醫療與檢驗合作端 | 提供資格、服務、排程、受理、履約與正式通知。 | 提供受授權的資料與工具接口。 | 由平台決定病情、照護或臨床資源配置。 |
| 使用者 | 提供行政偏好、檢視來源、選擇服務端、確認交接。 | 編輯條件、撤回或取消交接草稿。 | 將平台摘要視為醫療判斷。 |

平台可把已公告的服務層級、地點、時段、交通／到府條件、費用揭露與正式入口以一般人可理解的方式呈現。任何需要臨床判斷的分級由合作端的既有流程承接，原型不自動決定。

### 2.2 包含

- 文字、語音轉文字與表單輸入。
- 行政條件 schema：地點、可用時間、交通／到府偏好、已公告服務類型、聯絡偏好。
- 來源、更新時間、資料狀態與「模擬資料」標籤。
- 服務卡比較、地圖／撥號／外部預約入口的模擬動作。
- 使用者確認頁、模擬預約交接、狀態機、失敗回復與稽核紀錄。
- 管理端檢視：工具呼叫、輸入／輸出 schema、狀態轉換與錯誤原因。

### 2.3 排除

- 病情判讀、症狀分類、科別判定、檢傷、緊急程度判定、治療建議、處方與檢驗結果解讀。
- 真實患者健康資料、病歷、檢驗結果、健保身分資訊與支付資料。
- 真實預約寫入、派遣、診療、採檢、檢體運送、結果通知與任何 SLA 承諾。
- 對外宣稱醫療服務、保證時效或宣稱服務端可受理。

## 3. 詳細作法與系統思路

### 3.1 元件分工

| 元件 | 責任 | 禁止事項 |
|---|---|---|
| 使用者前台 | 收集可編輯行政條件、顯示來源與流程狀態、取得確認。 | 不將症狀輸入改寫為醫療建議。 |
| LLM 結構化服務 | 只把自由輸入轉成 schema 允許的行政欄位；產出欄位缺失提示。 | 不生成服務可用性、臨床內容或未經工具回傳的事實。 |
| 政策與 schema 驗證器 | 驗證欄位、阻擋臨床意圖、決定允許的工具。 | 不以規則代替醫療判斷。 |
| MCP 編排層 | 以最小權限調用已授權的服務目錄、地圖、正式入口與合作端 Adapter。 | 不直接提供資源、繞過使用者確認或擴張工具權限。 |
| 服務目錄 Adapter | 回傳固定快照的服務資料、來源、更新時間及資料等級。 | 不回傳未標示真相來源的資料。 |
| 預約／狀態 Adapter | 模擬送出、受理、拒收、取消與完成等事件。 | 不連接真實服務端或建立真實預約。 |
| 稽核日誌 | 記錄會話 ID、同意版本、工具名稱、請求摘要、結果、時間及狀態轉換。 | 不保存自由輸入中的敏感健康內容。 |

### 3.2 受控工具設計

1. `parse_administrative_request`：輸入使用者文字；輸出 schema 欄位與缺失欄位。
2. `search_service_catalog`：只接受已確認的行政欄位；輸出固定服務卡與來源資訊。
3. `open_contact_or_map`：回傳模擬的電話、地圖或正式入口動作，不直接執行。
4. `create_handoff_draft`：建立未送出的交接草稿。
5. `confirm_handoff`：需要使用者明確確認；在 Prototype 僅改變模擬狀態。
6. `get_handoff_status`：從模擬事件資料讀取狀態與失敗原因。

每個工具均採固定輸入／輸出 JSON schema、最小權限與 allowlist。LLM 不能直接讀寫資料庫，也不能自行建立服務資料或預約結果。

### 3.3 資料與狀態模型

**資料標籤：**每筆服務資料至少包含 `source_name`、`source_url`、`retrieved_at`、`data_status`（公開快照／合作端模擬／未知）與 `mock=true|false`。

**交接狀態：**`草稿 → 待使用者確認 → 已模擬送出 → 模擬受理／模擬拒收／模擬取消 → 結束`。任何工具錯誤走向 `送出失敗`，並保留草稿。畫面不得顯示「已預約」字樣，僅顯示「模擬交接已送出」。

### 3.4 介面與 Prototype 產出物

- 消費者端 6 個畫面：入口、行政欄位確認、服務清單、服務比較、交接確認、交接狀態。
- 管理端 3 個畫面：資料來源檢視、工具稽核紀錄、狀態與失敗回復。
- 固定測試情境 4 組：一般查找、偏好到府、資料過期、模擬拒收。
- 假資料資料集、OpenAPI／MCP 工具契約草案、狀態轉換表、風險文案清單。

## 4. 使用者路徑與邏輯流程

```text
使用者輸入文字／語音／表單
  → 安全檢查：阻擋臨床判讀要求，顯示固定說明與正式緊急入口
  → LLM 轉行政 schema
  → 使用者檢視並修改條件
  → 服務目錄 Adapter 查詢固定資料
  → 顯示服務卡：來源、更新時間、模擬標示、聯絡／地圖／入口
  → 使用者選擇服務
  → 建立交接草稿，揭露模擬範圍與資料用途
  → 使用者明確確認
  → 預約 Adapter 回傳模擬狀態
  → 顯示結果或可回復的失敗原因
  → 寫入最小化稽核紀錄
```

| 階段 | 使用者目標 | 系統行為 | 成功條件 | 失敗回復 |
|---|---|---|---|---|
| 入口 | 快速說明服務偏好。 | 擷取行政欄位。 | 欄位可讀、可修改。 | 要求補充缺少欄位。 |
| 服務選擇 | 比較可查到的服務。 | 依固定資料排序，顯示來源與資料狀態。 | 使用者能辨識資料是否為模擬。 | 資料不足時回到條件調整。 |
| 交接確認 | 決定是否送出。 | 建立草稿，揭露資料與模擬性質。 | 有明確確認紀錄。 | 未確認時不改變狀態。 |
| 狀態查看 | 了解交接結果。 | 讀取 Adapter 事件。 | 狀態、時間與原因可追溯。 | 顯示失敗原因與重新建立草稿。 |

## 5. grill-me 可行性審查

| 反思問題 | 檢視結果 | 處置 |
|---|---|---|
| 原型是否把行政協調偽裝為醫療判斷？ | 有風險。自由文字可能包含病情描述。 | 僅抽取行政欄位；阻擋臨床問題；固定顯示正式緊急入口。 |
| LLM 是否可能捏造服務可用性或預約結果？ | 有風險。 | 服務卡與狀態只由 Adapter 回傳；輸出加 schema 驗證與來源標籤。 |
| 未串接合作端時，是否能宣稱閉環？ | 不可。 | 使用「交接流程原型」名稱，所有預約與狀態標為模擬。 |
| 這個原型能驗證市場需求嗎？ | 無法。 | 市場驗證留給獨立訪談與邀約；文件不使用需求已成立的措辭。 |
| 是否需要真實健康資料？ | 不需要。 | 使用合成情境與最小化行政資料，禁止上傳病歷或檢驗結果。 |
| 是否要先做付款、地圖或真實 API？ | 不需要。 | 第一版以按鈕互動和 Adapter fixture 展示契約；正式串接列為後續 gate。 |
| 是否存在法規與廣告風險？ | 存在。 | 僅限內部 Prototype；加上明確非醫療、模擬與不提供診療聲明；上線前法務審查。 |
| 平台是否被誤認為服務提供者？ | 有風險。 | 首頁、確認頁與狀態頁都標示平台的協調角色、實際服務提供者與資料責任。 |
| 哪些條件出現就停止？ | 臨床功能、敏感資料、無法追溯的狀態或未標示模擬資料。 | 阻擋建置或移除該功能，回到規格修訂。 |

## 6. 驗收條件

1. 所有畫面可完成四組固定情境，且每一條服務資料都標示來源、資料時間與模擬狀態。
2. LLM 輸出通過行政 schema；針對臨床要求回傳固定限制文案，不產生醫療內容。
3. 未經確認不會進入「已模擬送出」；送出後每個狀態均有事件 ID、時間與失敗原因。
4. 原型資料庫與日誌不含真實患者資料、病歷、檢驗結果或支付資料。
5. 文件、程式介面與畫面不出現真實可預約、即時受理、醫療建議或 SLA 的宣稱。

## 7. 後續決策 Gate

完成原型後，才可決定是否進入市場與供給驗證。該決策至少需要：受訪者招募與訪談記錄、兩個潛在合作端的資料欄位與交接意願、法務對資料流程與對外文案的書面意見。未取得前，不開始真實預約、支付、到府服務或健康資料串接。
