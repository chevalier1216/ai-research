# 臺灣低門檻醫療服務鏈 AI 賦能｜可行性策劃與審查問答

## 結論

臺灣可建立接近美團「低門檻服務入口」的消費者體驗：使用者以文字、語音或欄位輸入所在地、可用時段、交通／到府偏好與要找的已公告服務；系統提供有來源、更新時間、地圖、電話、正式預約入口與合作端狀態；使用者自行選擇服務端後完成預約或交接。

首個可商業化範圍應限定為 **非臨床服務協調平台**。平台負責服務發現、行政條件整理、地圖／電話、預約交接、付款交接與履約狀態。合作醫療機構、居家照護團隊、檢驗所與持照人員負責受理、派遣、診療、採檢、檢體處理、結果說明與病歷。

投資前須同時取得三項條件：

1. 單一城市至少兩個醫療／居家服務合作端，提供可更新的服務範圍、時段、受理規則與正式入口。
2. 12–15 名非緊急服務搜尋者訪談中，至少 8 人能指出兩個以上查找或聯絡摩擦，且願意使用來源明示的服務入口。
3. 合作端以書面確認資料責任、API／深連結、個資同意、取消規則、客服分工與不自動化事項。

「兩小時內快篩結果」不得列為產品承諾。它只能是特定合作端、服務區、採檢項目、檢體運送與排程能力共同支持的 SLA；目前沒有足以支持臺灣全區服務或固定時效的公開證據。[L-04、G-01]

| 3. 比較與選擇 | 比較電話、地址、服務條件、可預約時段與費用揭露。 | 地圖、導航、撥號與合作端預約工具。 | Google Maps 僅供地圖／導航；可受理量由合作端確認。 | 無 API 時提供正式頁深連結或撥號。 |
| 4. 預約／付款交接 | 明確確認服務端、時間、費用與個資授權。 | 透過 MCP 或後端 API 呼叫預約、付款或深連結。 | 合作端排程、支付與服務條款。 | 呼叫失敗時顯示失敗原因、保留草稿、不建立假預約。 |
| 5. 合作端履約 | 合作端受理、派遣、到府服務或通訊診療。 | 平台顯示合作端回傳狀態。 | 醫療機構、居家團隊、檢驗所與持照人員。 | 合作端拒收或無量能時，回到可選服務目錄。 |
| 6. 結果後銜接 | 查看合作端核准的後續聯絡或預約入口。 | 呈現合作端固定文案與官方連結。 | 合作端正式通知與醫療流程。 | 不產生檢驗分析或處置內容。 |

## 需要的 AI、工具、程式與資料

| 類別 | 必要元件 | 作用 | 必要條件與限制 |
|---|---|---|---|
| 使用者 App | Web PWA、Android／iOS App、語音輸入、可編輯表單 | 低門檻輸入、地圖、撥號、使用者確認與訂單狀態。 | 介面必須固定顯示正式緊急聯絡入口；不得以症狀文字改變緊急程度或服務建議。 |
| LLM | 支援 JSON Schema／函式呼叫的模型服務 | 將自由語句轉為地點、時間、交通、服務類型與偏好等行政欄位；產生可讀說明。 | 每次輸出經 schema、規則與政策檢查；不得作臨床推論。OpenAI Responses API 可串接函式與遠端 MCP 工具。[T-09] |
| Skills | 需求正規化、服務查找、來源呈現、預約交接、狀態說明 | 將 AI 行為拆成最小權限工作單元。 | 每個 Skill 固定輸入／輸出、資料範圍、允許工具、拒絕條件與稽核事件。 |
| MCP 伺服器 | 服務目錄、地圖、預約、支付、狀態等工具介面 | 讓 AI 以受控 schema 呼叫工具。 | HTTP MCP 可採 OAuth 2.1；MCP 不提供合作端授權、可用人力或醫療資格。[T-05] |
| 服務目錄 | 健保署院所／診所資料集、合作端服務目錄 | 提供名稱、地址、電話、科別、固定時段與服務類別。 | 健保診所資料集每日更新，可作基礎名錄；實際受理、排程、到府範圍與費用須由合作端資料確認。[NHI-01] |
| 地圖與聯絡 | Google Places Text Search、Maps URLs、Android `ACTION_DIAL` | 地圖查找、路線、電話撥號與正式聯絡。 | Places 場所資料與地圖路線不代表服務可受理；`ACTION_DIAL` 保留使用者自行撥號確認。[T-01～T-03] |
| 合作端 API | REST／FHIR adapter、預約、服務區、容量、價格、支付與狀態 API | 取得真實可售／可預約資料，完成服務交接。 | FHIR `Appointment` 可作排程交換模型；臺灣採用、寫入權限與資料欄位需個別談定。[T-06] |
| 事件與工作流 | webhook、事件匯流排、工作流引擎、重試佇列 | 追蹤預約送出、受理、取消、派遣、完成與失敗。 | 訂單狀態與臨床資料分層；FHIR `Subscription` 只提供事件模型，仍需撤銷與權限治理。[T-07] |
| 資料庫與稽核 | 交易資料庫、加密金鑰管理、不可竄改稽核日誌、權限服務 | 保存最小化行政資料、同意紀錄、工具呼叫與狀態轉換。 | 病歷、醫療、健康檢查資料屬特種個資；需合法依據、告知、同意、安全維護與存取控制。[L-05、L-06] |
| 身分與同意 | OIDC、同意版本、撤回、目的與保存期間設定 | 驗證使用者、取得可追溯授權。 | OIDC 僅解決身分與技術授權；臺灣健康資料的同意與責任仍須依個資法與合作契約處理。[T-04、L-05] |
| 後台與人工營運 | 合作端後台、客服工單、事件監控、例外處理面板 | 管理資料更新、拒收、取消、申訴與工具失敗。 | 人工人員不得替代持照者作醫療判斷；醫療問題導回合作端。 |

## 法規、責任與合作條件

| 項目 | 必要條件 | 策劃要求 |
|---|---|---|
| 通訊診療 | 由合法醫療機構及符合規定的醫師承接。 | 平台只導向合作端流程，不宣稱平台提供診療。[L-01、L-02] |
| 醫療業務 | 無資格執行醫療業務有法律風險。 | LLM、客服與規則引擎均不判定病情、檢傷、處方或解讀結果。[L-03] |
| 到府服務 | 臺灣已有居家醫療由特約院所團隊提供。 | 只和具資格的合作端做封閉試點；先驗證地區、服務對象、運送、時效與地方要求。[L-04、G-01] |
| 健康資料 | 病歷、醫療、健康檢查資料受個資法特別保護。 | 服務發現階段只留行政最小資料；健康與檢驗資料交由合作端正式流程；建立同意、加密、權限、日誌、刪除與通報程序。[L-05、L-06] |
| 文案與行銷 | 非醫療機構的招徠性醫療廣告有風險。 | 文案限於服務資訊、合作關係、費用與正式入口；法務預審對外頁面、推播與客服話術。[L-07] |

## 階段化推進與停止條件

1. **第 0 階段：資料可用性。**整合健保公開名錄與兩個合作端服務目錄；每筆標示來源、更新時間與資料責任。
2. **第 1 階段：無交易服務入口。**只提供查找、地圖、電話與正式頁深連結；量測搜尋完成率、撥號／跳轉率與資料缺失率。
3. **第 2 階段：單一服務類別預約交接。**合作端提供可寫入或可追蹤的預約入口；使用者確認後才送出。
4. **第 3 階段：封閉到府服務試點。**限合作端定義的區域、服務項目與時段；每個 SLA、取消、拒收與結果通知均由合作端書面確認。
5. **停止條件。**少於 6 名受訪者感到明顯摩擦、合作端無法提供可更新資料、資料或工具流程出現未授權健康資料、AI 產生醫療判斷、或交易狀態無法回溯時，停止擴大試點。

## 審查問答紀錄

### Q1：使用者入口能做到多低門檻？

**答：**使用自然語句、語音與少量欄位即可開始。系統只抽取所在地、時間、交通／到府偏好與服務類型。每個欄位可修改，服務端由使用者自行選擇。

### Q2：平台如何避免跨進診療？

**答：**產品規格排除症狀判讀、科別判定、檢傷、治療、檢驗解讀與處方。通訊診療與病歷流程由合作醫療機構承接。[L-01～L-03]

### Q3：健保公開資料可支援到什麼程度？

**答：**可支援院所名稱、地址、電話、科別、服務項目與固定時段等基礎目錄。健保署診所資料集更新頻率為每日。可受理量、臨時休診、到府區域、價格與派遣能力必須另接合作端資料。[NHI-01]

### Q4：Google Maps、電話與導航在閉環中的角色？

**答：**它們解決找路與聯絡。Places 可回傳場所資料，Maps URLs 可開啟導航，`ACTION_DIAL` 可開啟撥號畫面。這些工具不執行預約、派遣或醫療判斷。[T-01～T-03]

### Q5：LLM、Skills、MCP、合作端 API 如何分工？

**答：**LLM 整理使用者輸入；Skills 限制每項工作與資料範圍；MCP 以 schema 和權限呼叫工具；合作端 API 回傳真正可服務、可預約與已履約狀態。每次交易工具呼叫都需要使用者確認。

### Q6：MCP 能否直接解決供應與履約？

**答：**不能。MCP 管理工具介面與授權流程。供應能力、醫療資格、服務範圍、排程、派遣與結果通知仍取決於合作端資料、契約與人力。[T-05、T-06]

### Q7：到府快篩能否作為首發服務？

**答：**可作後續封閉合作試點。首發前需確認合法服務主體、採檢項目、服務區、檢體運送、實際時效、結果通知、拒收條件與地方主管機關要求。公開資料不足以支持固定時效承諾。[L-04、G-01]

### Q8：健康資料如何處理？

**答：**服務發現只處理行政最小資料。健康與檢驗資料走合作端同意與權限流程。平台保留目的、同意版本、工具呼叫、狀態轉換與撤回紀錄；建立加密、權限分層、存取日誌與刪除程序。[L-05、L-06、T-04、T-08]

### Q9：最小可行商業閉環是什麼？

**答：**單一城市、單一非臨床服務類別、兩個合作端、已更新服務目錄、地圖／電話、正式預約交接、合作端狀態回傳與人工例外處理。此範圍可量測使用者摩擦、資料品質與合作端轉換。

### Q10：何時可以擴大到美團等級的多服務入口？

**答：**完成單城市試點後，再逐項增加服務類別與合作端。每增加一類服務，都需重新確認資料欄位、資格、責任、SLA、客服與法規影響。
