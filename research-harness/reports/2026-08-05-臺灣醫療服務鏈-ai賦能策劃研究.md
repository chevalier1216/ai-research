# 臺灣醫療服務鏈 AI 賦能研究｜從需求入口到合法履約的策劃內容

## 研究摘要

本研究評估：在不做診斷、檢傷、治療或選定院所的前提下，能否把使用者從「不知道該用哪一種服務、怎麼聯絡、何時可用」帶到可自行確認的正式服務入口，並讓合法服務端承接後續履約。

**研究結論：**臺灣已有院所地圖與條件查詢、受法規約束的通訊診療，以及個別院所的到宅服務；但公開資料未證實有把自然語句、服務條件、地圖、可用時段、預約、到府採檢與結果後銜接統一成單一消費者流程的服務。[MH-01–04] 海外的美團與 Halodoc 證明「入口→服務目錄／合作提供者→履約」是可存在的模式，但不能證明臺灣的需求、時效、供給或法規可直接複製。[MH-05–06]

首個優先商機為 **「非臨床服務協調層」**：把使用者的自由描述轉成可編輯的行政條件（所在地、可出門與否、可接受時段、想找的已公告服務），用合作提供者的正式資料與地圖／電話工具提供選項；使用者自行選擇後，轉入院所、檢驗或居護提供者的既有預約與履約流程。其商業可行性仍待臺灣供給合作、實際需求與付費意願驗證。

## 範圍與方法

- **結論市場：**臺灣；中國大陸、印尼與印度僅為競品／流程參考。
- **研究邊界：**服務發現、行政條件整理、正式入口、預約／聯絡與進度追蹤；不提供病症判斷、緊急程度判定、診療建議、處方或檢驗結果解讀。
- **證據方法：**兩個獨立蒐證工作包（醫療、生鮮）各自交接，之後由本報告只採納可連回公開一手來源的主張。企業公告僅用來證明其宣稱的功能，不當作需求或成效證據。
- **關鍵限制：**沒有臺灣消費者訪談、轉換率、付費意願、院所即時排程、到府採檢供給或結果時效資料；因此所有商業主張均為條件式。

## 終端消費者服務鏈策劃

### 服務命題：可信的「健康服務入口與履約協調」

使用者可輸入自然語句，例如「今晚沒交通工具，想找附近可聯絡的已公告服務」，但產品**不解讀病情**。系統只把句子拆成行政條件、列出來源與更新時間，並提供可由使用者選擇的正式入口。這不是 LLM 單獨服務：LLM 只是一個降低輸入門檻的元件；Skills 定義可執行的受限工作能力，MCP 讓 AI 受控呼叫地圖、服務目錄、排程與狀態工具，而院所／居護／檢驗合作端的正式 API 或資料同步才是可用性與履約的真相來源。

| 階段 | 使用者體驗 | AI／系統職責 | 必要合作與資料 | 不可跨越的邊界／失敗回復 |
|---|---|---|---|---|
| 1. 表達需求 | 輸入文字／語音，或選擇所在地、時段、是否可出門等偏好；介面固定顯示官方緊急聯絡入口，使用者可自行選擇使用。 | LLM 將輸入轉為可編輯的行政欄位，要求使用者確認。 | 不需健康資料即可先做服務查找。 | 不判讀、分類或推測症狀的緊急程度；不因文字內容改變服務建議。 |
| 2. 服務發現 | 看見附近／可聯絡的院所或已合作的到府服務，並看到資料來源、營業／服務條件與最後更新日。 | 規則引擎依地點、時段、服務項目與合作範圍篩選；地圖工具顯示位置、電話與導航連結。[MH-01、MH-07] | 官方院所／合作服務端的服務目錄為真實來源；地圖 API 僅輔助。 | 不排序「哪家最適合醫療上」；資料缺失或過期時標示並改提供官方查詢與電話。 |
| 3. 使用者選擇與銜接 | 使用者選擇一家服務端後，可撥號、開啟導航、進入院所預約頁或合作端排程。 | 保存使用者已確認的行政摘要，減少重複填寫；顯示尚缺資料。 | 院所／居護／檢驗合作 API 或正式連結。 | 無 API 時只能深連結或電話，不能假裝已預約。 |
| 4. 合法履約 | 合作端決定是否受理、安排訪視／診療／採檢、提供服務與結果。 | 顯示合作端回傳的狀態；提醒使用者查看正式訊息。 | 持照醫療、居護、檢驗與物流提供者；資料處理契約。 | AI 不作收案、派遣、採檢、診斷、報告解讀或治療決定。[MH-02–04] |
| 5. 結果後銜接 | 結果或服務完成後，使用者可查看合作端提供的正式後續選項、再次預約或聯絡。 | 以提供者核准的固定文案和連結呈現行政下一步；追蹤是否已完成聯絡。 | 合作端的結果通知與服務說明。 | 不以 LLM 自行「分析結果」或給處置；需要醫療說明時回到提供者。 |

### 商機候選與判斷

| 候選 | 使用者摩擦 | 商業價值假說 | 證據強度 | 現階段判定 |
|---|---|---|---|---|
| H-01：服務入口與行政協調層 | 服務入口分散，使用者需要自行從地圖、電話、院所頁與不同服務端拼接流程。 | 對院所／居護／檢驗合作端提供可轉換、具來源的入口與預約前資料準備；可採 B2B2C 服務費或合作分潤。 | **中**：入口、服務端與海外協調模式已證實；臺灣需求／轉換未證實。 | 優先研究與試點候選。 |
| H-02：合作到府採檢服務鏈 | 無法出門者需要確認服務區、時段、費用、是否可安排，以及結果後正式銜接。 | 與特定縣市的居護／檢驗／院所合作，將服務條件、排程與狀態整合。 | **低至中**：局部臺灣供給與海外模式存在；即時供給、時效、付費與授權未證實。 | 僅限合作端共同定義的封閉試點，不得先承諾「2 小時結果」。 |
| H-03：LLM 自動解讀快篩／檢驗並給處置 | 使用者可能想立即理解結果。 | 看似降低不確定性。 | **低且風險高**：本輪沒有臺灣合法性、臨床安全或需求證據。 | 不列入產品候選；只能做合作端已核准結果通知與正式諮詢入口。 |

## 技術與營運設計原則

1. **LLM 負責理解與編排，不負責醫療結論。**輸出採固定欄位：地點、時間、交通／到府偏好、已公告服務類型、使用者確認內容；所有欄位可編輯。
2. **Skills、MCP、API 是不同層次。**Skills 規定「只能查找已公告服務、不得做醫療判定」；MCP 將地圖、服務端目錄、排程、聯絡與狀態工具以權限與輸入／輸出契約提供給 AI；合作端 API／資料同步則提供服務範圍、可預約量、結果通知與履約狀態。沒有合作端授權，即使有 MCP 也不能聲稱可預約或到府。
3. **以服務端資料作為真相來源。**地圖 API 可協助查找、電話與導航，但營業、可收案、排程、結果時間必須由合作端資料或正式頁面確認。[MH-07]
4. **先做單城市、有限服務目錄。**全臺服務目錄與即時派遣的資料維護成本高；應先鎖定一個城市、少數合作服務與明確服務時段。
5. **健康資料最小化。**在服務發現階段只收集必要行政資料；需要傳輸健康或檢驗資料時，改由合作端正式流程、明確同意、權限與保存規則處理。
6. **不把電話／導航視為完成。**每一次深連結、撥號、預約送出、合作端受理與履約狀態都要有可觀察事件，否則不能宣稱縮短等待或提高轉換。

## 風險、未知與後續調研

- **核心未驗證需求：**臺灣使用者是否因服務資訊分散而放棄、誤用資源或願意為協調服務付費。本輪不能回答。
- **供給未驗證：**每個目標縣市的合作服務項目、服務半徑、可預約量、取消規則、結果時效與責任分工。
- **必要的下一步研究與預先門檻：**
  1. 招募 12–15 名在最近 3 個月曾為自己或家人尋找**非緊急**服務的臺灣成人，其中至少 6 名曾受交通、時間或照顧限制；不在實際急迫事件中招募或測試。記錄從需求到成功聯絡／預約的步驟、耗時、放棄點與既有替代方案。
  2. 對至少 2 家院所、1 家居護或檢驗合作端，取得服務目錄、資料責任、排程介接與不可自動化清單的一手確認。
  3. 僅在同時滿足以下條件時推進 H-01 的單城市、單一服務類別合作試點：至少 8 名受訪者能指出兩個以上資訊／聯絡轉換步驟，並願意在情境任務使用「來源明示的服務入口」；至少 2 個合作端能提供可更新服務條件與正式轉介入口；情境測試不得產生任何醫療判斷輸出。量測完成正式入口的比例、行政摘要修改率、聯絡成功率與拒收原因，不量測或推論醫療成效。
  4. 若少於 6 名受訪者認為現有流程有顯著摩擦、合作端無法提供可更新資料，或任何受試流程誘發醫療判斷，停止試點；改回純資訊可用性研究或請示是否更換服務類別。
  5. 若為 6–7 名受訪者，視為矛盾訊號：不啟動交易或服務試點，不把結果寫成需求成立；彙整反例與未解釋差異，請使用者決定是否縮小客群、限定一種服務，或不再投入。
