# 臺灣生鮮食材服務鏈 AI 賦能研究｜從一句需求到使用者確認後結帳的策劃內容

## 研究摘要

本研究要回答的是：臺灣家戶能否從一句條件輸入（人數、天數、預算、料理時長、飲食偏好與可等待的配送時間），獲得可確認的餐點與食材方案、商家候選、購物車與結帳入口，而不必逐一搜尋、換算與重組。

**研究結論：**臺灣已公開商品選購、購物車、結帳與冷凍配送的交易末段；以愛上新鮮為例，使用者可自行選商品、加入購物車、登入、確認訂單與配送，但配送實際時間由宅配安排，並非平台可保證。[MF-01–02] 本輪沒有找到臺灣零售商公開「一句條件→餐單→即時可售商品→可結帳購物車」的一手證據。海外 Instacart 已公開該完整的單一零售生態鏈，阿里千問／淘寶展示同一商業生態內從對話到交易的可能性，Samsung Food 展示上游的餐點、清單與照片輸入。[MF-03–05]

最有可能商業化的切入點不是跨所有零售商的萬能購物代理，而是 **「單一合作零售商的 AI 餐點到購物車協調層」**：LLM 把自然語句轉成可修改的約束，規則與食譜／食材資料產出餐點及食材需求，MCP 受控調用商家已授權的商品、即時庫存、價格、替代、配送、購物車與結帳工具；使用者確認商家、替代與總價後，才由商家交易系統送單。沒有這些供應商資料與權限，產品只能提供建議或深連結，不能宣稱一鍵下單。

## 範圍與方法

- **結論市場：**臺灣；中國大陸與全球案例僅比較產品／資料／履約結構。
- **研究邊界：**餐點與食材規劃、商家商品候選、價格／庫存／配送條件呈現、使用者確認、購物車與結帳交接；不做自動付款、未經確認替代、未授權爬取或跨商家假整合。
- **商業化前提：**Skills 用來限制每一項 AI 工作能力；MCP 把可授權工具的輸入、輸出與權限收斂；商家 API 或受控資料同步提供商品、價格、庫存、配送與結帳的真相來源。LLM 不能取代這三層。
- **證據限制：**本輪未取得臺灣家戶的直接任務資料、轉換率、付費意願或零售商 API 授權；海外功能不得用作臺灣市場大小或採用率證據。

## 終端消費者服務鏈策劃

### 服務命題：一句需求到「可購買、可確認」的單一商家購物車

使用者可以說「兩人吃五天、預算 2,000 元、每餐 30 分鐘內、週五晚上前送到」，但輸出必須是可調整的餐點與食材候選，而不是未經資料約束的生成文字。LLM 只降低輸入門檻；Skills 規定它能做什麼；MCP 受控呼叫工具；商家 API／資料同步決定什麼真的可買、何時可送、如何結帳。

| 階段 | 使用者體驗 | AI／Skills／MCP 職責 | 真相來源與履約系統 | 使用者控制與失敗回復 |
|---|---|---|---|---|
| 1. 一句條件輸入 | 輸入人數、天數、預算、料理時長、偏好與配送限制；可跳過未知欄位。 | LLM 以「需求正規化」Skill 轉成結構欄位並追問缺少的可計算條件。 | 使用者確認的輸入。 | 不確定食材或預算時列成假設，不把它視為事實。 |
| 2. 餐點與食材配置 | 檢視多個餐點組合、份量、預估食材與準備時間。 | 「餐點規劃」Skill 以食譜、份量與規則模型生成可替換組合；MCP 僅讀取已授權食譜／營養資料。 | 維護中的食譜與食材換算資料庫。 | 使用者可鎖定／移除餐點；資料不足時不產出精確份量。 |
| 3. 商家商品比對 | 選定一家合作商家後，看到對應 SKU、包裝規格、價格、替代品與無法對應的食材。 | 「商品匹配」Skill 以規則、同義詞與商家目錄比對；MCP 呼叫商家商品／價格工具。 | 商家授權商品目錄與價格 API／同步資料。 | LLM 不得自行捏造 SKU；比對信心低時要求使用者選擇。 |
| 4. 可售性與配送計算 | 看見本次可買清單、可替代方案、總價與配送選項。 | 「履約核對」Skill 透過 MCP 讀取即時／準即時庫存、配送區域、時段與最低門檻，重新計算購物車。 | 商家庫存、配送、促銷與物流／支付系統。 | 無資料或過期時只標示「待商家確認」；不得承諾庫存或送達時間。[MF-02、MF-06] |
| 5. 確認、加車與結帳 | 使用者選定商家、確認替代與總價後，才一鍵加車並到商家結帳。 | 「交易交接」Skill 僅在顯性確認後透過 MCP 呼叫購物車／結帳工具，或開啟商家深連結。 | 商家購物車、登入、支付與訂單系統。 | 沒有正式 API 時只可深連結或匯出清單；不得自動付款或跨商家合併結帳。 |
| 6. 訂單與替代追蹤 | 使用者查看商家回傳的訂單、缺貨與替代狀態。 | 「狀態說明」Skill 將商家事件轉成可讀提示；不改寫商家訂單。 | 商家訂單 webhook／查詢 API。 | 未有事件 API 時只導回商家訂單頁，不偽造追蹤狀態。 |

### 技術與合作架構

| 層次 | 角色 | 必要條件 |
|---|---|---|
| LLM | 理解自由語句、提出缺少條件、產出可修改的候選說明。 | 不直接決定 SKU、庫存、價格、配送或付款。 |
| Skills | 將工作拆成需求正規化、餐點規劃、商品匹配、履約核對、交易交接與狀態說明。 | 每一 Skill 有固定輸入／輸出、不得越權與可審計記錄。 |
| MCP | 提供受權限控管的食譜、商品、庫存、配送、購物車、地圖與訂單工具介面。 | 每次工具呼叫限定商家、資料範圍與使用者已確認的意圖；MCP 本身不等於資料授權。 |
| 商家 API／資料同步 | 商品、價格、庫存、替代、配送時段、購物車、登入、支付與訂單事件。 | 合作契約、資料更新 SLA、錯誤碼、回退流程與使用者授權。 |
| 規則與事件層 | 份量／包裝換算、預算總計、最低配送門檻、替代優先序與狀態機。 | 規則版本化，與 LLM 生成內容分離；所有交易前重新核對。 |

## 商機候選與分階段判斷

| 候選 | 核心摩擦／價值 | 證據強度 | 商業模式方向 | 現階段判定 |
|---|---|---|---|---|
| F-01：單一零售商餐點到購物車協調層 | 家戶以自然條件完成餐點與食材規劃，再依即時供給形成可確認的一家商店購物車。 | **中**：海外完整結構已證實；臺灣已具交易末段；但本地需求與 API 未證實。 | 白標 SaaS／導購與轉換分潤／合作商家增購功能。 | 優先候選；先找一個商家合作，不跨店。 |
| F-02：多商家比較與由使用者選店 | 將同一份食材需求比較為多家可買方案，讓使用者選一家再結帳。 | **低至中**：技術可拆分；本地商品、庫存、支付與合規授權未證實。 | 比價或導購服務費；需每家商家資料合作。 | 次階段；無 API 時只可提供可驗證候選與深連結。 |
| F-03：自動跨商家下單／付款 | 看似能一鍵完成所有採買。 | **低**：沒有本地跨商家資料與支付授權證據。 | 聚合交易平台。 | 不列入初期範圍；高責任、結算與客服成本。 |

## 需求驗證、風險與下一步

- **未證實的消費者需求：**臺灣家戶是否願意為餐點到購物車協調付費，或是否會因現有手動做法放棄採買／增加時間成本。本輪不能以海外調查代替。
- **關鍵商業風險：**商家沒有 API 或商品資料品質不足時，體驗會退化成不可靠建議；若承諾一鍵結帳但只能深連結，會直接傷害信任。
- **下一步研究與預先門檻：**
  1. 招募 12–15 名臺灣主要採買者：最近 8 週至少採買生鮮兩次、每週規劃至少 3 餐，且其中至少 6 名有預算或到貨時間限制。以真實一週餐點、預算和送達時間完成情境採買；量測從需求到商家購物車的時間、手動搜尋次數、替代接受度與放棄點。
  2. 與至少一家候選零售商確認商品／價格／庫存／配送／購物車／訂單介接方式、更新頻率、替代與支付權限；未取得前不得宣稱一鍵結帳。
  3. 僅在同時滿足以下條件時推進 F-01 的「一家商家、20 個常見餐點、有限地區」驗證：至少 8 名受訪者在任務中主動修改或補足既有手動採買流程，並表示願意使用可先檢視再結帳的候選車；合作商家能以 API 或受控同步提供商品、價格、庫存與配送條件；至少 90% 的測試食材需求可產生可解釋的商品候選，且所有無法匹配項目被明確標示。比較 AI 候選與手動採買的完成率、修改率、總價差、無法匹配率和成功進入結帳比例。
  4. 若少於 6 名受訪者發現顯著規劃／搜尋摩擦、商家無法提供可更新資料，或候選車出現未揭露的價格／可售性錯誤，停止全鏈交易試點；改為只研究餐點規劃或請示是否更換合作商家。
  5. 若為 6–7 名受訪者，視為矛盾訊號：不啟動交易試點，不把結果寫成需求成立；彙整哪些客群、餐別或採買情境有差異，請使用者決定是否縮小客群、限定單一場景，或不再投入。
