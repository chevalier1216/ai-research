# H-01｜健康服務入口與履約協調：策劃規格

> 狀態：**研究候選，未驗證、不得實作或對外承諾。**只有完成本文件的進入門檻並取得使用者確認後，才能交給 Codex 或其他工作分支規劃專案。

## 要解決的問題

消費者面對非緊急健康服務需求時，可能需要跨地圖、院所頁、電話與不同服務端自行找入口與確認條件。產品目標是降低**行政查找與銜接**門檻，而不是解釋病症、判斷緊急程度或提供處置。

## 目標終端體驗

1. 使用者輸入位置、可用時段、交通／到府偏好與想找的**已公告服務類型**。
2. LLM 將語句轉成可編輯的行政欄位；固定顯示官方緊急聯絡入口，但不判讀使用者文字。
3. 系統用合作端服務目錄、地圖與聯絡工具列出具來源、更新時間與條件的選項。
4. 使用者自行選擇後，透過正式預約頁、撥號或合作 API 交接。
5. 合作端受理、安排與提供服務；產品只呈現合作端回傳狀態與其核准的後續入口。

## 商業化系統邊界

| 層次 | 必要責任 |
|---|---|
| LLM | 結構化與說明；不得診斷、檢傷、選院、解讀檢驗或給治療建議。 |
| Skills | 限制為行政需求正規化、服務查找、來源呈現、交接與狀態說明。 |
| MCP | 受權限控管地呼叫地圖、服務目錄、合作端預約與狀態工具；記錄每次呼叫。 |
| 合作端 API／資料同步 | 服務範圍、時段、可收案、預約、履約與結果通知；是唯一真相來源。 |
| 人員／持照提供者 | 受理、派遣、採檢、診療、結果說明與醫療決定。 |

## 非目標

- 不承諾 2 小時結果、到府可用性、等候時間或服務適宜性。
- 不在沒有合作端 API／正式入口時偽裝成已預約。
- 不收集超出服務發現所需的健康資料；健康／檢驗資料走合作端的同意與權限流程。

## 進入實作前的硬門檻

1. 12–15 名符合條件的臺灣非緊急服務搜尋者訪談中，至少 8 人可指出至少兩個資訊／聯絡轉換摩擦，並願意使用來源明示的入口。
2. 至少 2 個合作端可提供更新中的服務條件與正式轉介入口；至少 1 個可明確說明資料責任與不可自動化行為。
3. 情境測試不產生醫療判斷；未授權資料與工具呼叫為零。
4. 6–7 人為矛盾訊號，需請示是否縮小客群或服務類別；少於 6 人、資料不可更新或出現醫療判斷時停止。

## 需要使用者確認的事項

- 第一個試點城市、服務類別與合作端。

- 合作端資料、個資與責任安排是否已完成書面確認。
