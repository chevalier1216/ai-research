# F-01｜單一零售商餐點到購物車：策劃規格

> 狀態：**研究候選，未驗證、不得實作或對外承諾。**只有完成本文件的進入門檻並取得使用者確認後，才能交給 Codex 或其他工作分支規劃專案。

## 要解決的問題

家戶可能要把人數、天數、預算、料理時長與配送限制轉成餐點與商品清單，並在商品規格、可售性與配送條件下重複搜尋。本候選先以**單一合作零售商**做完整服務鏈，不假設跨商家整合或自動付款。

## 目標終端體驗

1. 使用者用一句話輸入條件，並確認系統正規化的需求欄位。
2. 系統提出可修改的餐點、份量與食材需求。
3. 使用者選定一家合作商家後，系統以其授權資料顯示 SKU、包裝、價格、可售性、替代與配送條件。
4. 使用者確認商家、替代與總價；系統才加車並導向商家結帳。
5. 訂單與缺貨狀態由商家事件回傳；沒有事件 API 時只導回商家訂單頁。

## 商業化系統邊界

| 層次 | 必要責任 |
|---|---|
| LLM | 將自然輸入轉為可修改的限制與候選說明；不得捏造 SKU、價格、庫存或配送。 |
| Skills | 需求正規化、餐點規劃、商品匹配、履約核對、交易交接、狀態說明；各自有固定輸入／輸出。 |
| MCP | 受權限控管地呼叫食譜、商家目錄、庫存、配送、購物車與訂單工具；使用者確認後才可呼叫交易工具。 |
| 商家 API／資料同步 | 商品、價格、庫存、配送、替代、購物車、登入、支付與訂單狀態；是唯一真相來源。 |
| 規則／事件層 | 份量與包裝換算、預算加總、配送門檻、替代規則與訂單狀態機；與生成內容分離。 |

## 非目標

- 不做跨商家合併購物車或付款。
- 沒有合作 API 時不宣稱一鍵加車、即時庫存、優惠或送達時段。
- 不未經確認替代商品、不自動送單或付款。

## 進入實作前的硬門檻

1. 12–15 名符合條件的臺灣主要採買者任務訪談中，至少 8 人看見規劃／搜尋摩擦，並願意使用先檢視再結帳的候選車。
2. 至少 1 家合作商家能以 API 或受控同步提供商品、價格、庫存與配送條件，並書面確認購物車／結帳權限。
3. 20 個常見餐點的測試中，至少 90% 食材需求能產生可解釋候選，所有未匹配項都明確揭露；未揭露價格或可售性錯誤為零。
4. 6–7 人為矛盾訊號，需請示是否縮小客群或餐點情境；少於 6 人、資料無法更新或出現未揭露交易錯誤時停止。
